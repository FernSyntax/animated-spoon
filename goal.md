# GOAL — Kingdoms of Dominion

## 0. Mission and execution contract

Build a complete, real-time, persistent, massively multiplayer 4X strategy game inspired by the mechanics and player experience of Evony and Avatar: Realms Collide, using original names, content and assets. Deliver a working reference game and reusable engine, not a pitch, scaffold, mockup or architecture-only demo. Multiple human players must share live realms, grow cities, form alliances, march armies, fight monsters and each other, capture territory and compete for control of the realm. The game continues when players are offline.

Priority: authoritative correctness and security > complete playable systems > recoverability and operational scalability > usability > visual appearance. Make the interface simple and fully functional. Use only text, geometric shapes, colors, simple procedural symbols and lines; no external art or asset generation, expensive rendering, or copied IP.

Target architecture: 1,000,000 concurrent connected players globally, initially modeled as 200 realms with 5,000 CCU each, plus operational headroom. This is a capacity design target, NOT a measured claim. Build a sharded architecture and distributed workload generator that can test it. Do not claim achieved scale, platform certification, production readiness or SLO compliance without actual evidence. No paid infrastructure, app-store accounts, or million-client run is necessary to complete the local implementation. Clearly separate local acceptance, production validation and deployment blockers.

Execute autonomously in the current repository. Inspect tools and code first. Preserve compatible work but do not preserve incompatible single-player/SQLite/browser-wrapper architecture. Follow this file rather than making up scope. Pin a compatible stable toolchain and dependencies, commit lockfiles and keep implementation straightforward. No unresolved mandatory TODOs, fake endpoints, dummy buttons, in-memory substitutes for durable gameplay, mocked multiplayer, or tests skipped to manufacture success. Keep a PROGRESS.md with milestones, evidence, failures and next concrete action; update after each slice and reread this file after context compaction. Do not weaken the contract.

## 1. Fixed technology decisions

- Backend: stable Rust (Cargo workspace), Tokio async runtime, Axum HTTPS/WS edge API, Tonic gRPC internal RPC, Prost/Protocol Buffers, SQLx with PostgreSQL and real versioned migrations. Use structured tracing, OpenTelemetry instrumentation, Prometheus metrics and Grafana dashboards.
- Client: one Flutter/Dart application using Flutter widgets for HUD, menus and panels and Flame for a lightweight 2D interactive map. Build targets: Android, iOS, Windows, macOS, Linux and web. Native targets use Flutter's native rendering and compilation, not WebViews or browser wrappers. No Electron, Tauri, Capacitor, Unity, separate platform gameplay implementations, or required Node application runtime. Normal generated platform runners/build files are allowed. Use platform-neutral HTTP/WebSocket libraries, generated Dart protobuf types, clear state management and adaptable touch/mouse/keyboard input. Do not put authoritative game rules on the client.
- NATS JetStream for durable asynchronous event distribution; Valkey for disposable cache, presence and rate limits. Neither is the source of truth for game state, money, inventory, timers or troop ownership. A temporary cache/broker outage must not lose committed gameplay.
- Docker images; Docker Compose for local multi-process deployment; Kubernetes manifests or Helm chart for scalable production deployments; OpenTofu modules with documented provider assumptions. Choose one concrete example production deployment (AWS/EKS + managed PostgreSQL is acceptable) while keeping application portable. No cloud provisioning without explicit authorization. Provide exact local run/test commands and CI jobs.
- No service-per-game-feature architecture. Keep strongly related game rules within a realm's transaction boundary. Prefer explicit modules and ordinary Rust types over novel frameworks or speculative abstractions. No unsafe Rust in owned code unless justified and audited.

## 2. Deployment topology and ownership

Use one monorepo and Cargo workspace. Suggested crates: domain (IDs, invariants, commands/events), content, simulation, application, persistence, protocol, configuration, observability, test-support. Suggested binaries: gateway, control-plane, realm-worker, outbox-worker, loadgen; share libraries. Flutter in clients/game; canonical proto files in proto/; migrations, content, infra, docs, scripts and tests at root. Exact module boundaries may be adjusted without violating ownership.

- Global control plane: account identity, credentials/sessions, realm directory, realm membership/provisioning, routing and admin. Global PostgreSQL separate logical database from gameplay. Login/realm selection must not require scanning all realms. Use globally unique IDs and explicit realm IDs. Account-to-realm membership/provisioning is retryable and reconciled; do not use distributed SQL transactions.
- Stateless horizontally scalable gateways: authenticate, limit requests, maintain WS sessions, route to realm worker, filter/forward authorized deltas, handle reconnect/backpressure. They do not mutate gameplay tables directly. Internal RPC carries verified principal and realm context; service authentication and trust boundaries are explicit. Do not trust client player IDs.
- Realm workers: each realm has exactly one fenced active mutation owner at a time, with standby/failover. A worker can host multiple small realms; a realm can be relocated without changing player IDs. Realm workers serialize conflicts via bounded command queues and/or short ordered DB transactions, with concurrency for independent work only if correctness is demonstrated. Do not place all realms behind one global lock or queue. Scheduler, gameplay and state commit use the same ownership boundary. All gameplay writes must verify ownership/fencing in the transaction; stale workers cannot commit after ownership transfer. Document lease renewal, takeover, DB time and fencing implementation, and test old-owner rejection. No correctness dependence on Kubernetes pod uniqueness or a Valkey lock alone.
- Realm PostgreSQL: canonical state, durable schedule, command deduplication, reports, audit/ledger and transactional outbox. All mutable gameplay for a realm lives within one database transaction boundary. Multiple realms can share a cluster initially; distribute realms across independent DB clusters using an explicit shard/realm directory and pool limits. Every primary/foreign key and query must enforce realm scope where relevant. Include at least two realms and demonstrate separate DB routes or two shard databases locally. No cross-shard join in the gameplay hot path. Global outages must have a documented effect on existing sessions.
- Spatial chunks are interest/indexing boundaries, not independent writers. No cross-realm combat, economy or alliance membership in the initial game; seasonal cross-realm war is a future extension using a separate event realm and explicit transfer protocol. Do not implement live migration or geographic write partitioning without a demonstrated need. Provide safe offline realm movement/restore runbook instead.
- Outbox: insert events with state mutation in one PostgreSQL transaction. Publish to JetStream with stable event IDs. Handle redelivery, duplicates, lost acknowledgments and broker outage. Consumers are idempotent. Use bounded retry/backoff, dead-letter/error visibility and retention policies. Never treat message delivery as exactly-once. Use broker notifications to fan out changes, never to decide combat or resource ownership.

## 3. Authoritative simulation and protocol

Use discrete-event simulation, not per-player or per-troop high-frequency ticks. A building upgrade, training queue, research, gathering, march, rally or shield has a persisted deadline. Use indexed due-event queries, bounded batches, stable order (due_at, explicit priority, stable ID), an injectable clock, and a scheduler that works with zero connected clients. Each event completion, effect, deduplication and follow-on schedule is atomic. After crash/downtime process overdue events in order; do not silently discard progress. Handle catch-up with bounded transactions, fairness, backlog metrics and readiness. Do not execute new commands ahead of due conflicting events. Document authoritative time and same-timestamp semantics; clock must not go backwards for a realm. Test exact boundary times and delayed processing equivalence.

Resources accrue lazily from elapsed time with integer/fixed-point arithmetic and persisted fractional remainders. Apply production changes at their effective time, handle capacity saturation correctly, and never depend on how often clients poll. No floats for authoritative resources, troop quantities or costs. Checked arithmetic and explicit limits prevent overflow. Troops are aggregate counts, not millions of independently simulated entities. Deterministic battle engine with documented versioned formulas and persisted RNG seed if used. Stable tie-breakers; no nondeterministic map iteration affecting results.

All mutations are typed commands with authenticated player, realm, command ID and validated payload; include expected version where useful. Return typed accepted/rejected result with command ID, authoritative state/version and meaningful error codes. Deduplication is scoped to realm/principal/command ID and stores outcome in the same transaction; conflicting reuse of ID with different payload is rejected. Handle retries after a committed response is lost. Reject unauthorized, cross-realm, negative, excessive, stale or impossible actions; never trust client costs, clocks, troop totals, positions, results or entitlement. Atomic resource debit, troop reservations, unique destination claims and conservation invariants. Lock rows consistently or serialize conflicts and retry known transient DB failures safely. No acknowledged success before commit.

Use versioned protobuf envelopes and generated Rust/Dart bindings from one schema. HTTPS for authentication/bootstrap and WS binary frames for commands, results and live updates; gRPC internal. Support heartbeat, bounded frame sizes, sequence/versioned snapshots and deltas, reconnect with missed-update recovery or authoritative snapshot, rate limiting, slow-consumer eviction, backpressure, and session expiry/revocation. Avoid a global unfiltered stream. Snapshot plus delta handoff must not lose updates; if uncertain, resync. Use per-subscription sequence or cursor with explicit gap detection, not assumptions that unrelated realm events will arrive at all clients. Restrict private data at server before encoding. A client may interpolate march positions/timers from server timestamps; it cannot complete them. Show pending/failed command status and actual server results. Use HTTPS/WSS outside explicit local development.

## 4. Playable world, progression and economy

Implement original content in versioned, validated data catalogs; seed repeatable development worlds. Make game feel like a mobile kingdom builder: continuous progress, persistent cities, march queues, alliance conflict, territorial objectives and a long-term progression loop. No hardcoded demo-only outcomes.

- Realm: deterministic seeded 2048 x 2048 logical tile world, sparse/chunked 32 x 32 indexing (configurable smaller for tests); plains/forest/hills/water/mountains; valid unique placements, accessible starting positions, world coordinate jump, camera pan/zoom, visibility rules, tile selection and minimap/overview as simple geometry. Terrain can be generated on demand with stable seed. World entities: player cities, resource nodes, monsters, NPC forts, neutral subordinate cities, capital/strongholds and active marches. No materializing or broadcasting every tile on every request. Spatial subscription limits, nearby tile deltas and private account updates. Use passability and deterministic bounded pathfinding or documented deterministic routes; prevent unbounded CPU on requests.
- Accounts: register/login/logout, select realm, create city once per realm with durable player progression, real concurrent human players. Dev seed includes at least two separate usable accounts, two realms and NPC targets. Account security: vetted password hashing (Argon2id), expiring/revocable sessions, secret configuration, no credentials in logs, browser Origin policy and secure transport in production. Local demo credentials explicitly disabled outside dev mode.
- Resources: food, wood, stone, iron, gold; production, storage limits, spending, loot and gathering. One primary city plus optional subordinate cities (bounded, e.g. six total). Seed neutral conquerable subordinate cities so players can expand before any human has a subordinate city; the same siege and capture rules apply. Switch and manage each owned city. Each city has buildings, balances, queues and garrison; resource transfers are timed marches. City placement and conquest are transactionally exclusive.
- Buildings: Town Hall, Farm, Lumber Mill, Quarry, Iron Mine, Market, Warehouse, Barracks, Academy, Wall, Hospital, Embassy/Rally Hall; at least 10 levels each, escalating costs/time, prerequisites and real effects. Show level, next effect, cost, duration, queue and reason for rejection. At least one construction queue per city. Train/research/construct complete on server even offline. Configurable early action times seconds/minutes for play; test speed/clock is server-configured only and disabled in production.
- Research: at least 10 technologies x 3 levels (economy, logistics, military, defense); dependencies, real modifiers, one player research queue. Research affects actual economy, march capacity/speed or combat. No cosmetic technologies.
- Military: infantry, ranged, cavalry, siege, scouts; at least 3 tiers for combat types, meaningful attack/defense/speed/cost/carry stats, prerequisites, quantity training, wounded capacity, healing and garrisons. Troops committed to marches cannot train/dispatch again. At least 3 simultaneous marches per player, with research/building upgrades increasing capacity. Heroes: at least 6 catalog heroes; recruit via earned resources, level via experience, equip one hero to a march, meaningful combat/economy bonuses, exclusive assignment. No gacha or purchases. Inventory: earned items including resource bundles and speedups; atomic use, bounded speedup of own active queues; no premium payment.
- NPC monsters: five levels, real combat and rewards, exclusive kill reward, respawn deadlines. Resource nodes: finite stock, gathering duration/capacity, replenish, contest behavior and return loot. NPC forts: conquerable territory objective with real defense and cooldowns. NPC actions use ordinary combat validation; no fake human accounts.

## 5. Multiplayer warfare and social systems

- Shared persistent march state machine: dispatch, traveling, arrival, gathering/rally/combat, returning, completed/cancelled. Scout, hunt, gather, attack city/fort, reinforce, transport, recall, rally and return. Reserve troops/resources/hero atomically at dispatch. Persist route, speed, timestamps, mission, target, state version and payload. Recall invalidates old completion events atomically. Resolve changed ownership/target death/invalid attack on arrival against current state; return safely or documented losses. A returning army whose home was lost routes to an eligible owned city or documented loss; never credit an enemy city. No duplicate troops, rewards or hero assignment.
- Combat on arrival (Evony-style, not continuous per-frame RTS combat). Deterministic troop matchups, tier stats, heroes, research, wall, reinforcements and optional terrain modifiers. Document formula and casualty rounding; both attacker/defender can lose units; separate wounded/dead; bounded loot debited from defender; troop/resource conservation including documented sinks/sources. Battle reports contain inputs, bonuses, casualties, loot, outcome and timestamp, visible only to participants/authorized allies. Same inputs replay identically. Tests prove weak armies lose and modifiers matter.
- PvP city siege: protection shield with clear duration and rules, scout before attack, wall/defense damage, plunder, repeat attacks leading to subordinate city capture if permitted. Primary cities are not permanently removed: when defeated they lose eligible loot/defense and enter a defined recovery/relocation state with protection. Captured subordinate city transfers buildings/eligible resources/territory in one transaction; explicitly resolve former owner queues, wounded, reinforcements and outgoing armies, no free enemy troops. Set a clear city cap, and predictable fallback when cap reached. No friendly fire or shield bypass. All constraints enforced on dispatch and arrival as applicable.
- Alliances: create, apply/invite/join/leave, accept/reject, roles leader/officer/member, kick/transfer leadership, membership limit, permission checks, alliance chat, member list, rankings and territory. Rally: leader creates with target/deadline, allies commit troops and optional heroes from real garrisons, rally launches once and resolves as a coordinated attack, returns survivors and distributes rewards deterministically; cancel/leave rules preserve troop ownership. Reinforce allied cities with visible garrisons and recall. Alliance help reduces eligible construction/research time with per-task/per-helper caps and no duplicated benefit. Define race rules for leaving/kick while committed.
- Territory: capture forts/strongholds with ownership and a simple adjacent/radius influence rule; contest/capture changes ownership atomically. Realm capital is a high-value periodic objective; occupation and leaderboard/season score provide a win milestone without deleting player progression. Provide documented scoring and deterministic tie handling. Real-time world and alliance chat with authentication, access control, message size/rate limits, mute/block and basic reporting; not publicly expose private chat. Inbox and battle reports, attack notifications and event history. No real-money monetization, cross-realm wars, voice chat, user asset uploads, elaborate hero equipment, full trading marketplace or continuous field interception in mandatory scope.

Support resume/reconnect after backgrounding, expiry and switching devices. Browser/native networking must use same protocol, not separate API implementations. Avoid dependencies unavailable on any target; isolate unavoidable platform integrations (secure storage, networking config) behind interfaces. Native token storage and browser security strategy must be documented; don't store plaintext passwords. No client-side secret keys.

Reachable screens: authentication/realm selection, home/city overview, buildings, research, troops/training/hospital, heroes/inventory, map/tile action dialog, march/rally list, alliance management, chat/inbox, battle reports, rankings/season objectives and settings. Every mandatory action and its legal parameters must be reachable through visible UI, including account creation, PvP, rallies, joining/leaving, recalling, speedup, capture and switching cities. No empty placeholder routes, fake timers or developer-only buttons. Show resource balances and rates, queue timers, troop availability, map legend, attack warnings, server connection state and understandable errors. UI reflects server-confirmed changes and visibly recovers stale state. ## 7. Data integrity, operations and security

- Enforce primary/foreign keys, unique constraints, nonnegative quantities, scoped ownership, schema checks and indexes for hot queries. Persist versioned content references, UTC deadlines and event ordering. No destructive production reset. DB migrations reviewed for backward compatibility; document rollout/rollback and restore. Backups and point-in-time recovery design; test actual backup/restore of local DB and compare pending events and state. Database synchronous durability settings and HA policy define acknowledged-write RPO; do not promise zero loss across untested regional disasters.
- Bounded pools, queues, payloads, subscriptions, per-user/realm rate limits, timeouts, cancellation, retry budgets, load shedding and graceful shutdown. No unbounded per-connection buffers or full-map broadcasts. Gateway/worker health/readiness; drain on deploy; recover worker ownership and overdue schedules without duplicate effects. Broker/cache outage behavior explicitly tested. NATS/Valkey/database/admin ports not publicly exposed in production manifests. Least privilege, separate credentials, TLS, network policies and resource requests/limits; secret templates only. Authentication, authorization and tenant isolation tested; abuse/malformed frames cannot crash process. Audit administrative mutations. Production admin endpoints private and authenticated.

## 8. Capacity model and realistic testing

Design for 200 active realms x 5,000 concurrent players, plus headroom (e.g. 30%). Treat realm capacity as hypothesis. Baseline per connected client: 0.2 mutations/sec and 0.5 read/subscription operations/sec; allow overlapping PvP spikes of 2 mutations/sec per active participant and popular chunk fanout. At 1M CCU this implies 200k mutations/sec and 500k read/subscription ops/sec globally before retries, plus scheduled work and outbound deltas. At 5k CCU/realm baseline 1k mutations/sec and 2.5k reads/sub ops/sec. Model connection memory, gateway CPU, DB transactions and IOPS, timers, fanout bandwidth, storage/retention and shard counts; document assumptions, formulas, bottlenecks and measured vs projected numbers. Never assume Rust makes these achievable automatically.

Rust headless loadgen uses real production auth/protobuf/WS/API, deterministic seeded workloads, independent accounts, persistent actions (build/train/research/gather/PvE/PvP/alliance/rally), viewport changes, reconnects, hot-spot scenarios and configurable distributed agents. Provision test accounts safely via normal or private test-only interfaces. No bypass of authoritative checks. Aggregate command success/rejection, throughput, p50/p95/p99, scheduler delay, reconnect results, DB/outbox lag and resource utilization with workload, duration, hardware, versions, failures and raw results. Separate expected game-rule rejections from system errors. Include idle, realistic mixed, hotspot war, reconnect storm, worker failover and restart scenarios. Run at least a real 20-client multi-realm smoke and a 100-client mixed workload for >=60 seconds if environment supports; run higher stages as resources permit. Test two independent clients contending for one target, and at least two gateway/worker instances. If runtime capacity is insufficient, run lower real stage, document actual limits and mark unmet acceptance, never fake success. Provide runnable staged profiles for 1k/5k per realm and 10k/100k/1M distributed CCU plus headroom; do not execute expensive external tests without authorization.

Production targets (not automatic pass): p95 committed command latency <100ms within region under baseline, p99 scheduled event lag <1s, p95 relevant map update <250ms, 99.99% service availability over defined SLO window, no duplicate committed effects, no lost acknowledged writes within defined tested HA failure model. Document measurement boundaries, SLO scope, exclusions, sample sizes, and scaling runbook; local tests do not certify global SLOs. Provide methodology to find sustainable saturation and safe operating point. No million idle sockets masquerading as game load.
